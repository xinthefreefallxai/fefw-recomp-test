# Configuration reference

Settings come from an ini file and from environment variables. The lookup order for a key is: environment variable, then ini value, then the default in the code. The runtime loads `nxrt.ini` from the working directory unless `NXRT_INI` or `InitOptions.ini_path` names another file; a missing file is not an error. Each key read is logged at Info level under the tag `config` with its value and its source (`env`, `ini` or `default`).

Rules:

- Section and key names are case-insensitive.
- Ini syntax: `[section]` lines, then `key = value`. A `;` or `#` that follows whitespace starts a comment. A quoted value is taken verbatim.
- The environment variable for a key is `NXRT_` plus the upper-case section, an underscore, and the upper-case key, with every non-alphanumeric character replaced by `_`. Example: `[diag] watchdog_seconds` is `NXRT_DIAG_WATCHDOG_SECONDS`.
- Integers accept decimal and `0x` hex. Booleans accept `1`/`0`, `true`/`false`, `yes`/`no`, `on`/`off`. Doubles must parse completely. Text that does not parse keeps the default.

### Audio notes

When the sink has a clock of its own (XAudio2, or `paced`), the audio renderer keeps about 40 ms of audio queued on it and renders the next 5 ms frame whenever the queue falls below that, instead of waiting on the host clock. The sound card and the host clock never agree exactly; pacing by the host clock alone would fill the queue slowly (frames dropped) or drain it (a click). With the null sink the renderer keeps its 5 ms host-clock pacing. The pace does not depend on the game's frame rate: the renderer runs on its own thread and the game's audio thread waits for the renderer's frame event.

`wav_dump` is read when the first audio sink is created and works with either sink. `device` and `volume` only affect the XAudio2 sink (the null sink plays nothing). `device` is read each time the XAudio2 sink opens. `volume` is read once, at first use, and can also be changed in code while the program runs.

`wav_dump` writes the game's sound to a WAV file as well as to the output device. Every frame that reaches the sink is written, including frames the device drops because its queue is full. The file header is updated about once a second of audio and again when the sink closes, so a file from a run that was killed is still playable up to the last update. If the sample rate or channel count changes during the run (for example a switch from stereo to 5.1), the next file gets a number before its extension: `dump.wav`, then `dump.1.wav`, and so on.

`device` chooses where the XAudio2 sink plays. `default` (or an empty value) uses the system's default output. Any other text is looked for first as an exact endpoint id, then as part of a device's friendly name, ignoring upper and lower case. The first match wins. If nothing matches, the log gets a warning and the default device is used. Each time the XAudio2 sink opens, the log lists the active output devices with their names and ids, so the text for this key can be copied from there.

While a sink is active, a line `sink <name>: queue avg A ms (min..max ms), underruns +N (total), dropped +D, written F frames/s (rate R)` is logged every `stats_interval` seconds. The queue is the audio waiting in the device, which is the output latency; `written` should match the rate (lower: the game is starved or the stream is stretched). When a sink closes, it writes one line to the log with its counters: frames written, accepted, dropped, underruns (times the device ran out of audio after playback had started) and the largest number of buffers queued at once.

## Keyboard beam and visor keys (`controls.ini`)

These live in the play-mode file `controls.ini` (key `[play] controls`), not in `nxrt.ini`. The F1 settings page writes the same file.

| Input | Action | What the game does |
|---|---|---|
| `1` | `beam_1` | Power beam |
| `2` | `beam_2` | Wave beam |
| `3` | `beam_3` | Ice beam |
| `4` | `beam_4` | Plasma beam |
| `5` | `visor_1` | Combat visor |
| `6` | `visor_2` | Scan visor |
| `7` | `visor_3` | Thermal visor |
| `8` | `visor_4` | X-ray visor |
| Mouse wheel up / down | `beam_prev` / `beam_next` | Cycle the beams you own, in the order power, wave, ice, plasma. Off when `[mouse] wheel_beams = 0`. |

How it works: the game only knows the Switch pad, so an action is turned into pad buttons by the `[switch]` table. By default `beam_1` to `beam_4` hold X and press the d-pad (up, right, down, left), and `visor_1` to `visor_4` press the d-pad alone (up, right, down, left). The wheel skips beams the player does not have yet. In the menu and map contexts they are switched off (`1` to `8 = none` in `[bindings.menu]` and `[bindings.map]`) and the wheel moves the cursor or the map instead.

To change a key, add a line `Key = action` to `[bindings.all]` (every context) or to one context (`[bindings.gameplay]`, `[bindings.morph]`, `[bindings.scan]`, `[bindings.menu]`, `[bindings.map]`). `Key = none` switches an input off in that context. Key names are SDL scancode names (`Left Ctrl`, `Page Up`, `Mouse1`, `WheelUp`).

`[meta] defaults_rev` records the revision of the factory bindings that the file was written with. The game writes it. A file without the section counts as `0`. When a release adds a new factory binding, the game adds it to an existing `controls.ini` at the next start, but only where that key is still unbound in that context. A key you bound yourself is left alone. A file written before `[meta]` existed has no record of what you removed, so a key you had unbound there gets its new default once. After that, a key you remove stays removed. The first time this happens, the old file is kept next to it as `controls.ini.bak` (an existing `.bak` is never overwritten), and the upgraded file is written at once. The log has one line saying what was added. A file with no `[bindings.*]` section gets the whole factory set and is not rewritten. A revision can also change a factory value (revision 3: `[aim] lock_mode` to `free`). A file that still has the old factory value takes the new one at the same upgrade; any other value stays.

`[mouse] menu_cursor`, default `1`: in menus the mouse works like a pointer: a visible cursor, left click activates (in Pokopia: the selected entry, the pointer does not move the selection), right click goes back, the wheel scrolls. While it is on, the left click drives no binding in the menu and map contexts. The old key `menu_touch` is ignored; a file that still has it loads without a warning and nothing changes.

### Lock-on and camera feel (`controls.ini`, `[aim]` and `[camera]`)

`[aim] lock_mode`, default `free` (it was `classic` before defaults revision 3; a `controls.ini` still on `classic` from an older revision moves to `free` once, and a later choice of `classic` stays). `classic` is the game's own lock-on: the view turns to face the target. `free` starts the lock the same way, then centres the view on the target once. After that the mouse and right stick still turn the view, and the view is held so the locked target stays on screen inside the margin. The gun and reticle stay on the target, and shots home and strafing circle it, as in the normal lock. Releasing the lock returns to normal aim. The scan visor always uses the classic lock. See `docs/S32.md` for details.

`[aim] free_lock_margin`, default `0.15`, range `0` to `0.4`: the share of the screen kept clear along every edge while `lock_mode = free` holds the view. `0` lets the target reach the edge; `0.15` keeps it in the middle 70 percent.

`[camera] gun_drives_view`, default `1`. `1` is the game's own behaviour: the arm cannon is fixed to the view, so its idle drift, walking bob and landing dip move the whole view. `0` makes the view follow only the mouse and the stick. Those movements move the gun on screen instead, and the view stays still. Takes effect at once, no restart needed. Set it from the F1 page or the launcher, where it shows as "Steady view" (ticked means `0`).

Checked in a real game run with `tools/test/keys_check.py` (warp to `tallon_canyon_cavern`, grant the other beams and visors, press each key and read the game's own beam and visor numbers): `1` to `4` give power, wave, ice and plasma, the wheel steps wave, ice, wave, and `5` to `8` give combat, scan, thermal and x-ray.

### Start-up and menus (`controls.ini`, `[tweaks]`)

All off by default; with them off the game starts and plays as it always did. They are on the F1 page (Extras tab, "Start-up and menus") and on the launcher's Extras tab. See `docs/S46.md`.

`[tweaks] skip_intro`, default `0`. `1` skips the opening cutscene of a new game (the gunship landing on the Frigate Orpheon) without a key press. It uses the game's own cutscene skip: in the Exterior Docking Hangar the cutscene counts as skippable, and the skip button is pressed for the game the moment the game accepts it (about two seconds in), then the game fades out and jumps to the state the end of the cutscene leaves. Other cutscenes play as usual. Takes effect at the next new game.

`[tweaks] skip_boot_logos`, default `0`. `1` ends the title's 14 second intro movie (the logo forming) as soon as it starts, so the title screen with "press start" comes up at once.

`[tweaks] language`, default `auto`. The game's language: `auto` uses the Windows display language when the game has it, else English; a name such as `French` or `LatinAmericanSpanish` picks one (names as in `[system] language`). The launcher's Settings page (Language) and the F1 menu's Game tab set it. `[system] language` in the game ini wins over it. Applies at the next start.

`[tweaks] fast_menus`, default `0`, and `[tweaks] menu_speed`, default `2`, range `1` to `4`. With `fast_menus = 1` the front end (title, main menu, save slots, difficulty, options, extras) runs its clock `menu_speed` times faster: its animations, fades, waits and the attract-mode timer. The transition movies between the title, the main menu and Extras are cut after 1/`menu_speed` of their length. The looping movies behind the menus, their sound and the game itself keep their speed. `menu_speed` is read only while `fast_menus` is on. Applies at once.

### Glow colour (`controls.ini`, `[tweaks]`)

`[tweaks] glow_color`, default `off`: `off` keeps the game's colours. `R,G,B` (0 to 255 each, as a colour picker shows them) recolours the glows of Samus's equipment: the morph ball's glowing stripes, inner glow, boost glow, trail and light, the arm cannon's charge glow and lit panels, and the suit's lights (the visor glow and the small lights on the chest, belt, knees and shins, on all four suits, from their glow maps). The colour multiplies the game's glow, so the ball's white glow takes it exactly, the charge's yellow mixes with it (magenta gives a pink-red charge), and a darker colour gives a dimmer glow. The morph ball's shell keeps its colours. The cannon's panels and the suit's lights keep the game's brightness and take the setting's hue, for every beam. Their glow textures are recoloured as the game uploads them, which takes about a second in the background. A change applies at once, with no restart. Details in `docs/S44.md`.

`[tweaks] suit_glow`, `ball_glow` and `gun_glow`, default `auto`: `auto` follows `glow_color`, `off` keeps the game's colour for that part even when `glow_color` is set, and `R,G,B` gives the part its own colour.

The launcher's Tweaks tab and the F1 page's Tweaks tab have the switch, three sliders with a colour swatch, a Reset button that goes back to the game's colours, and the per-part choice. The F1 page shows the colour in the game while the sliders move; Apply and save keeps it.

`NXRT_GLOW_TEST_FILE` (environment, test aid): a file of `[tweaks]` lines. When it changes, its values replace the saved ones in the running game (checked twice a second).

`NXRT_GLOW_LOG_TEXTURES` (environment, discovery aid): `1` logs the identity (tail hash) of every sRGB ASTC texture the glow's texture hook sees, once each, while a glow colour is on. `WxH,WxH,...` also claims every texture of those sizes under a numbered discovery id without changing it, so the runtime's `edited by the host (id ...)` lines match each texture id to its tail. See `docs/S44.md`.

`NXRT_GLOW_TEST_FILL` (environment, test aid): `1` paints every glow texture texel in the glow colour at full strength, to show whether a texture reaches the screen.

### Suit and arm cannon colour (`controls.ini`, `[tweaks]`)

`[tweaks] suit_color`, default `off`: `off` keeps the game's paint. `R,G,B` (0 to 255 each) repaints Samus's suit in that colour, anything from black to white, keeping the shading and detail of the game's textures. The morph ball and the spider ball follow it. The visor, the lights painted on the suit and the glow keep their colours (the glow has `glow_color`).

`[tweaks] gun_color`, default `off`: the same for the arm cannon's shell (first person, every suit and beam).

Both are on the launcher's Tweaks tab and the F1 page's Tweaks tab (a switch, three sliders and a swatch each, and "Reset the paint"). A change shows in the game about a quarter of a second after the slider stops; the textures are repainted in the background (about 0.1 to 0.15 s per texture). Details in `docs/S45.md`.

`NXRT_TINT_TEST_FILE` (environment, test aid): a file of `[tweaks]` lines (`suit_color = ...`, `gun_color = ...`). When it changes, its values replace the saved ones in the running game (checked twice a second).

### Controller sticks (`controls.ini`, `[pad]`)

`[pad] deadzone`, default `0.10`, range `0` to `0.5`: the dead zone of the left stick (movement). Before the right stick got its own key, this was the only stick dead zone.

`[pad] stick_max`, default `1.0`, range `0.5` to `1.0`: how far the left stick must be pushed to count as fully pushed, as a fraction of its travel. At `1.0` nothing changes. Some pads (a worn DualSense, for one) top out at 0.9 to 0.97 of the range, so the game never sees a full push and the character moves slower than with the keyboard; lowering this to about `0.9` fixes that. The travel between `deadzone` and `stick_max` is rescaled to 0..1.

`[pad] right_deadzone`, default `0.10`, range `0` to `0.5`: the dead zone of the right stick (looking). A file with `deadzone` but no `right_deadzone` gives the right stick the value of `deadzone` when read. The next save writes both keys.

`[pad] invert_y`, default `0`: flips the right stick's vertical axis in play, so pushing up looks down. Menus and the map keep the stick as it is. It adds to the game's own invert option in its controls menu, so with both on, looking is back to normal.

`[pad] look_sens`, default `1`, range `0.25` to `3`: multiplies the right stick's deflection in play. Below 1, the top turn speed is lower. Above 1, it is reached sooner. Like `invert_y`, it applies in play only.

`[pad] ball_orbit`, default `2`, range `0` to `6`: how fast, in radians per second, the right stick turns the morph ball camera around the ball at full deflection. `0` turns the stick off and leaves the mouse on. `[mouse] ball_camera = 0` turns both off.

`[mouse] ball_camera`, default `1`: in the morph ball, the mouse and the right stick turn the camera around the ball. Moving the mouse left or right puts the camera on another side of the ball, and it stays there; the ball then rolls in the direction you see. Moving the mouse up or down raises or lowers the camera, between just above the floor and almost overhead. The vertical part goes back to normal when you leave the ball. Rooms with a fixed or scripted camera keep it. `0` gives you the game's own camera, which the mouse does not move. Details in `docs/S48.md`.

`[mouse] ball_sensitivity`, default `2`, range `0.1` to `20`: how fast the mouse turns the morph ball camera, on the same Source engine scale as the settings page (2 is the same speed as the default aim). It sets both directions. Older files with `morph_yaw` and `morph_pitch` (radians per count) still load. A vertical speed of its own can be kept by putting `morph_pitch = <radians per count>` after `ball_sensitivity`; the game writes it that way when the two differ.

## Window modes and the picture (`controls.ini`, `[display]`)

`window_mode` is `windowed`, `borderless` or `exclusive`. Borderless covers the display at its desktop mode. Exclusive asks Windows for the desktop mode. If the display refuses (a remote or locked session, some drivers), the game logs "window mode 'exclusive' was refused" and uses borderless instead. The setting in the file stays as it was. Alt+Enter and the F1 page switch modes while playing.

The game's picture size (internal resolution) is fixed when the game starts. It is the size of the window or screen at that moment, unless `render_width` and `render_height`, or `render_scale`, are set. Start in `borderless` on a 4K screen and the game renders at 3840x2160. Start windowed and press Alt+Enter, and the picture keeps the window's size and is scaled up, with bars when `keep_aspect = 1`. For a sharp full-screen picture, set the window mode before starting (the launcher does this), or set `render_width` and `render_height`.

`aspect`, default `auto`: the shape of the 3D view and the HUD. `auto` takes the window's shape at start (or the shape of `render_width` x `render_height` when both are set); `16:9`, `21:9`, `32:9`, `16:10` (any `W:H`) or a number from 1.0 to 5.0 forces one. Pokopia: on any shape but 16:9 the game's targets get that shape (1080 high when wider, 1920 wide when narrower, then `render_scale` on top), the 3D view is Hor+ (the game's vertical FOV, a wider horizontal one; narrower shapes keep the 16:9 width and show more above and below) and the menus and HUD stay 16:9, centred. `aspect = 16:9` keeps the 16:9 picture with bars. The log line `pkp: aspect ...` gives the size used, and the first widened camera logs its vertical and horizontal FOV.

`quality_preset` (`switch2`, `high`, `ultra`, `custom`) and `view_distance` (1.0 to 4.0), live, shown on the F1 Graphics page for games with quality hooks (Pokopia). Picking a preset sets `view_distance`, `lod_bias` and `anisotropy` together (Switch 2: x1, 0, game; High: x1.5, -0.5, 8; Ultra: x2, -1.0, 16); changing one of them afterwards makes it `custom`. Pokopia's view distance multiplies the far clip of the scene cameras when their projection is built (`pkp_quality.cpp`). `[pkp] quality_preset` / `view_distance` in the ini or the environment win over these.

On a picture narrower than 16:9 (16:10, 3:2, 4:3), the HUD and the menus keep their full 16:9 width and show more above and below. Wider pictures keep the HUD at 16:9 in the middle, as before.

The frame rate counter (`[fps] corner`) defaults to `top_left`. The bottom corners overlap the menu prompts and the title screen's copyright line.

New self-test steps (`NXRT_PLAY_SELFTEST`, see `play_selftest.h`). `gate:NAME` holds the script until the file `selftest_NAME` exists in the working folder. The file is then deleted and the script goes on. `report[:label]` logs the window mode, pixel size, focus and frame count.

## Test tooling keys (`[test]`, work area S5)

All off by default; details in `include/nxrt/tt.h` and `docs/S5.md`. Environment variable = `NXRT_TEST_<KEY>`.

| Key | Default | Meaning |
|---|---|---|
| `script` | empty | Scripted run (`.nxs`, grammar in `include/nxrt/tt_script.h`). Exit code 0 pass, 1 fail, 2 usage/parse error, 4 crash, 5 freeze, 6 process ended early, 124 wall timeout. |
| `enabled` | `false` | Turns the test tools on by themselves, without a script, record, replay, deterministic or trace key set. |
| `regions` | `regions.tsv` next to the script | Name table for `@area` / `@warp` (`name<TAB>world guid<TAB>area guid`). |
| `out` | `testout` | Output folder: `result.json`, `trace.jsonl`, `shots/`. |
| `deterministic` | `false` | Virtual clock (one frame = `clock_step_ticks`), seeded RNG, fixed wall-clock epoch. |
| `seed` | `0x5EED5EED` | RNG seed of deterministic mode. |
| `clock_step_ticks` | `320000` | Virtual ticks (19.2 MHz) per frame. |
| `frame_source` | `hook` | `hook` (needs `tests/sites/mpr_testtools.sites` in the lifted game), `tick` (`diag_frame_tick`), `svc:N` (a frame every N SVCs, bring-up), `manual` (tests). |
| `trace` | `<out>/trace.jsonl` | Per-frame JSON lines; `none` disables. |
| `record` / `replay` | empty | Record the live pad of every frame / feed a recorded input trace. |
| `replay_exit` | `false` | With `replay`: `1` ends the run where the recorded input ends. |
| `hash_regions` | empty | Memory folded into the frame hash: comma list of `0xADDR+0xSIZE` and `module:<name>` (the module's RW pages). |
| `max_frames` | `0` | Fail the run after this many frames. |
| `wall_timeout_s` | `900` with a script | End the run with exit code 124 after this long. |
| `freeze_exit` | `true` with a script | A watchdog fire ends the run with exit code 5. |
| `shot_dir` / `require_shots` | `<out>/shots` / `false` | Where `@shot` writes; a missing screenshot provider fails the run when set. |
| `game_base` | `0x7100000000` | Base of the game's main module (probe and hook addresses). |
| `warp_wait_loader` | `true` | `@warp` waits until the game's resource loader thread has been idle for 10 frames in a row before it starts the warp. Warping while the loader still builds assets for the old game instance crashed it in `CParticleStaticRenderState` (S42). `false` warps at once, as before. |
| `warp_loader_max_ms` | `30000` | How long `@warp` waits for the idle loader, in host milliseconds, before it warps anyway with a warning. |
